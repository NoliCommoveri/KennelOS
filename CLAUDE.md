# CLAUDE.md — KennelOS (Lite / Pro / Demo editions)

Local-first, static, multi-page dog-breeding records app (IndexedDB via Dexie, GitHub Pages, no
build step). Three editions off one shared core: the full app is under `shared/` and is what
**Pro** ships; Lite adds a cap + reduced surface; Demo is seeded read-only. The only server is
the opt-in cloud API in `cloud/` (Cloudflare Worker); the app must run identically without it.

## Docs
- Read **`README.md`** (summary, layout, doc map, current status) at the start of a session.
  History lives in `docs/BUILD_LOG.md`: append to it, don't read it by default.
- Consult only when the task touches them: `docs/KennelOS_Lite_Pro_Editions_Plan.md` +
  `docs/KennelOS_Lite_Cap_Enforcement_Spec.md` (edition intent);
  `docs/End_State_Design_and_Maintenance_Guide.md` (reference map of `shared/` code — read its
  `KennelOS/…`, `data/…`, `pages/…`, `sw.js` paths as `shared/…`); cloud/sync plans in `docs/`;
  `cloud/README.md` for server work.
- Undocumented or design-adjacent decision → ask / surface it before implementing.
- After a structural change (table/index/field, FK, entity, repo, page, event type, vocab,
  invariant), update the End-State guide and/or editions docs in the same change.

## Service worker — never skip
- Maintain only `shared/sw.js`; `dist/*/sw.js` is generated by `build/assemble.mjs` — never hand-edit.
- Adding/renaming/removing any app file → update `PRECACHE_URLS` in `shared/sw.js` in that same
  edit (one bad path breaks offline). Pro-only file → also add to `shared/data/proPages.js`.
- `CACHE_NAME` bump: **never on your own initiative.** When a batch seems done, ask "Ready to
  bump the SW cache, or more changes coming?" One bump per session/shippable batch; once bumped,
  later edits in the session ride that version.

## Architecture non-negotiables
- Multi-page static, ES modules, no SPA router, no CDN (vendor into `shared/vendor/`), offline after first load.
- Pages → repos → Dexie. Pages never touch `db.*` or `localStorage` (use a repo / `settings.js`).
- One thin repo per entity (`getById`, `getAll({includeArchived})`, `create`, `update`, `archive`, `hardDelete`).
- Shared core is edition-agnostic: no hardcoded caps or Pro/Lite checks. Edition specifics go via
  `shared/data/editionConfig.js` and `shared/data/editionTour.js` (overlaid per edition by
  `build/assemble.mjs`). Pro-only pages live in `pro/`, not `shared/`.

## Decided — do not re-litigate
- One `Dog` table for all dogs; life-stage change = `status` update, never a new record.
- One polymorphic `Event` table (`subject_type`/`subject_id`); module is `HistoryEvent`/`eventRepo`, never bare `Event`.

## Data conventions
- `id` = `crypto.randomUUID()`. Soft delete only (`is_archived`); no cascades.
- Date-only fields are `YYYY-MM-DD` strings; only `created_at`/`updated_at` are full ISO.
- **Schema is additive only.** Shipped `db.version(N)` blocks are frozen; a new table/index goes in
  a new version block listing only what it adds. A new plain field needs no block.
- **Backups stay backward compatible:** new fields optional with defaults; never rename/remove a
  shipped field/table/key; unknown fields skipped; device-only tables (`device_secrets`,
  `sync_meta`) never in a file. Bump format versions only when an older build couldn't read the file.
- Index only fields you query/sort on. Status/type vocab from `data/vocab.js`.
- Escaping: `listView` `cell` functions and hand-built innerHTML must `esc()` every user value.

## Registries — update when adding FKs or fields
- New FK → add it to `shared/data/referenceRegistry.js` (and the guide), or hard-delete orphans silently.
  Reverse relationships are derived queries, never stored back-pointers.
- New field → classify in `shared/data/syncRegistry.js` as `cloud`/`private`/`pending`. Making a
  field `cloud` is a privacy decision — surface it. Changing cloud fields → regenerate
  `node cloud/scripts/cloud-fields.mjs > cloud/src/lib/cloudFields.js`.
- New direct `db` write in the data layer must call `settings.markDataChanged()` or be exempted in
  `tests/cloudDirty.test.js` with a reason.

## Cloud
- Opt-in; `cloudUrl: null` must work (no requests, no cloud UI). Check `cloudConfig.isCloudAvailable()`
  first; live sync also gated by `editionFlags.liveSync`. Only `shared/data/cloud/cloudApi.js` touches the network.
- Server: new migration = new `.sql` + its line in `cloud/src/migrations/index.js`; never edit
  applied ones; never log emails/codes/tokens/bodies. Run `cd cloud && npm test`.

## Verification
- Serve repo root (`python3 -m http.server 8000`), open `/shared/`; never `file://`.
- `node --check` touched files; `node --test` from root (Node ≥ 22); `node build/assemble.mjs` for editions.
